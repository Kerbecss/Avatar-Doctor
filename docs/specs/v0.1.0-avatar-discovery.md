# v0.1.0 — Avatar Discovery

Status: **Draft — awaiting external approval**

This document is the canonical product and release contract for `v0.1.0`. The release plan may sequence this work but cannot redefine it.

## Goal

`v0.1.0` introduces Avatar Doctor's first functional behavior: discover VRChat Avatar Descriptors in currently loaded Unity scenes and let the user identify and select the avatar that Avatar Doctor should target.

## User value

When the user opens Avatar Doctor, they can immediately understand:

- that no avatars are present;
- that exactly one avatar is present;
- that multiple avatars are present;
- which avatar is selected; and
- how to choose another avatar manually.

## Scope

The release includes only:

- VRChat Avatar Descriptor discovery;
- valid, currently loaded Unity scenes;
- inactive avatar roots;
- deterministic candidate ordering;
- zero, one, and multiple candidate states;
- automatic selection;
- manual selection;
- explicit refresh and controlled event-driven rescanning;
- discovery-state presentation in the existing Editor window;
- safe Editor lifecycle and event cleanup;
- focused tests for discovery and selection behavior; and
- Unity validation of the completed feature.

## Explicit out of scope

The following are expressly outside `v0.1.0`:

- hierarchy snapshots;
- component inventories;
- asset inventories;
- reference graphs;
- diagnostics or validation findings;
- repairs;
- expression menus or parameters;
- animator analysis;
- material or shader analysis;
- PhysBones;
- contacts;
- Quest conversion or preparation;
- builds or publishing;
- a persistent public API;
- public VPM distribution or a public VCC listing;
- avatar mutation;
- scene mutation;
- asset mutation; and
- any work assigned to `v0.1.1` or later roadmap releases.

Selection persistence across a domain reload, project restart, or Editor restart is also out of scope.

## VRChat SDK integration decision

### Official evidence

The decision was verified against current official sources on 2026-08-21:

- the [VPM package format and version-range guidance](https://vcc.docs.vrchat.com/vpm/packages/) defines `vpmDependencies` and recommends a wildcard for the current VRChat SDK breaking line;
- the [official VRChat packages repository](https://github.com/vrchat/packages) identifies `com.vrchat.avatars` as the Avatars SDK package;
- the [official stable SDK 3.10.4 release](https://github.com/vrchat/packages/releases/tag/3.10.4) publishes `com.vrchat.avatars-3.10.4.zip`; and
- the [Public SDK API guidance](https://creators.vrchat.com/sdk/public-sdk-api/) requires redistributable packages to use supported public boundaries and recommends semantic version ranges instead of reflection over SDK internals.

The current stable Avatars SDK line is `3.10`. Avatar Doctor will support:

```text
com.vrchat.avatars: 3.10.x
equivalent range: >=3.10.0 <3.11.0
verified stable version: 3.10.4
```

Phase 1 will add this VPM dependency to the package manifest using the official syntax:

```json
"vpmDependencies": {
  "com.vrchat.avatars": "3.10.x"
}
```

This planning phase does not modify the package manifest or install the SDK.

### Selected architecture

Avatar Doctor is specifically a VRChat avatar tool. It will therefore use a supported compile-time dependency on the official Avatars SDK and the public `VRC.SDK3.Avatars.Components.VRCAvatarDescriptor` component type.

```text
Editor window UI
↓
Avatar Doctor candidate, result, and selection contracts
↓
VRChat-specific discovery integration
↓
Official VRChat Avatars SDK public types
```

VRChat SDK types may appear only inside the VRChat-specific integration. The candidate and selection contracts consumed by unrelated Core or UI code must not expose VRChat SDK types.

The package remains Editor-only. Inspection of the official `3.10.4` release package confirms that it contains the runtime `VRC.SDK3A` assembly definition and an auto-referenced `VRCSDK3A` runtime plugin containing the `VRC.SDK3.Avatars.Components.VRCAvatarDescriptor` type. Package metadata alone does not conclusively prove the minimal explicit reference required by Avatar Doctor's asmdef.

`VRC.SDK3A` is the intended minimal declared VRChat SDK asmdef reference while retaining `overrideReferences: false`. Phase 1 must verify that boundary through actual VPM package resolution and Unity compilation against a stable `3.10.x` SDK before discovery implementation proceeds. Any additional explicit VRChat SDK asmdef or precompiled-assembly reference requires external SPEC review. Reflection remains forbidden as a workaround.

The integration must not use:

- reflection as its primary or fallback production mechanism;
- type-name string matching;
- copied or vendored SDK source or assemblies;
- private or internal SDK APIs; or
- SDK types distributed through unrelated UI or Core contracts.

If the approved `3.10.x` boundary cannot compile against the public descriptor type with the intended minimal reference during Phase 1, implementation stops and returns to specification review. A broader assembly boundary or reflection is not an authorized workaround.

## Discovery semantics

### Scene source

Discovery considers only regular scenes returned by the loaded-scene set for which all conditions are true:

```text
scene.IsValid() == true
scene.isLoaded == true
EditorSceneManager.IsPreviewScene(scene) == false
```

For each qualifying scene, the discovery integration visits its root GameObjects and obtains descendant `VRCAvatarDescriptor` components with inactive descendants included. Each live descriptor component is one candidate.

Discovery does not query arbitrary project assets, prefab assets, unloaded scenes, Unity preview scenes, or the global Unity object population. Prefab Stage is a preview-scene editing context and is excluded. A prefab asset opened in Prefab Mode must not become a candidate, even when it contains a descriptor. Other Unity preview scenes are also excluded. A prefab instance in a qualifying regular loaded scene remains eligible because its component belongs to that scene.

Scene eligibility uses the supported Unity `2022.3` `EditorSceneManager.IsPreviewScene` API directly. `v0.1.0` does not introduce a general Stage abstraction.

Descriptors whose GameObject no longer belongs to the scene being scanned, has been destroyed, or belongs to an invalid, unloaded, or preview scene are discarded before the result is published.

### Inactive objects

Traversal includes inactive roots and inactive descendants. Active state does not affect eligibility or ordering.

### Multiple loaded scenes

All qualifying loaded scenes contribute candidates to one result. The active scene has no special discovery priority.

### Read-only operation

Discovery must never:

- mark a scene dirty;
- modify a GameObject or Component;
- write through `SerializedObject` or `SerializedProperty`;
- register Undo operations;
- save a scene;
- create, import, modify, or save an asset; or
- use project mutation as error recovery.

### Deterministic ordering

Unity enumeration order is not a product contract. Candidates are sorted with ordinal comparisons over this explicit key:

1. saved scenes before unsaved scenes;
2. normalized saved scene asset path, or loaded-scene index plus scene name for an unsaved scene;
3. hierarchy sibling-index sequence from scene root to descriptor GameObject;
4. ordinal hierarchy display path;
5. zero-based descriptor component ordinal on the same GameObject; and
6. descriptor instance ID as the final in-session tie breaker.

The descriptor component ordinal is the component's zero-based position among `VRCAvatarDescriptor` components in that GameObject's component order for the current discovery operation. It is computed before candidate sorting. The hierarchy display path includes GameObject names and sibling indices. Scene identity includes the saved asset path when available; an unsaved scene uses its name and loaded-scene index. Duplicate scene names and duplicate GameObject names therefore remain distinguishable.

Instance ID is never user-visible identity. It remains only the final in-session ordering and equality tie breaker if every preceding key is equal.

The order is deterministic for the current loaded scene state. Stability across a reload of unsaved scenes is not promised because persistence is outside this release.

## Candidate representation

`AvatarDiscoveryCandidate` is a small internal, immutable value containing only:

- an opaque live descriptor identity/reference owned by the discovery integration;
- the avatar root GameObject reference needed by the Editor;
- the internal deterministic zero-based descriptor component ordinal;
- a display name;
- scene identity; and
- hierarchy display path.

The opaque identity and component ordinal distinguish candidates that otherwise share the same GameObject, scene, hierarchy path, and name. The UI converts the ordinal to a one-based label only when disambiguation is necessary, such as `AvatarRoot — Descriptor 1` and `AvatarRoot — Descriptor 2`. The identity and ordinal are not serialized or persisted, and `VRCAvatarDescriptor` is not exposed beyond the integration layer.

The candidate does not contain component or asset inventories, diagnostics, performance data, hashes, hierarchy snapshots, or future-release fields.

## Discovery result

`AvatarDiscoveryResult` is immutable and contains:

- a read-only ordered candidate collection; and
- a derived count state: `None`, `Single`, or `Multiple`.

The state must agree with candidate count. Consumers cannot mutate the collection. Results are owned by the window/session instance; there is no mutable global singleton.

## Selection model

Selection state records either no candidate or one candidate and its origin: `Manual`, `AutomaticSingle`, or `AutomaticEditorSelection`. `Unresolved` means that candidates exist but no safe choice has been made.

### No candidates

```text
selected avatar: none
discovery state: None
selection state: empty
```

Any previous manual or automatic selection is cleared.

### Exactly one candidate

The sole candidate is selected automatically with origin `AutomaticSingle`. A stale manual identity is cleared. The UI explains that the only candidate was selected automatically.

### Multiple candidates after discovery refresh

Resolution uses this order:

1. preserve a valid manual selection;
2. otherwise preserve a valid current automatic selection when the refresh was caused by hierarchy, scene, window, or explicit Refresh activity;
3. otherwise map the active Unity Editor selection to exactly one candidate and select it with origin `AutomaticEditorSelection`; and
4. otherwise leave selection unresolved and require a manual choice.

The first candidate in display order is never selected merely because it is first.

### Manual selection

Choosing an entry in the Avatar Doctor control establishes a manual selection. It remains sticky across refreshes while the same live descriptor candidate exists, regardless of active Unity selection changes.

If the manually selected descriptor disappears, the manual state is cleared and the full automatic rules run against the new result. An invalid candidate can never remain selected.

### Active Unity Editor selection

If there is no valid manual selection, a selection-change event resolves against the current result without rescanning it:

- a Component maps through its GameObject;
- a GameObject maps to candidate roots that are ancestors of that object, including the object itself;
- when nested descriptor roots match, the nearest descriptor ancestor wins;
- if multiple descriptor components share the same nearest root, the mapping is ambiguous and no automatic choice is made;
- a selection outside every candidate root makes no new automatic choice; and
- when no new safe choice exists, a still-valid automatic selection is preserved, otherwise selection is unresolved.

A safe automatic mapping may replace a previous automatic selection, but it never overrides a valid manual selection.

### Persistence boundary

Candidate and selection state live only for the current Editor/window lifetime. `EditorPrefs`, `SessionState`, assets, scenes, and other persistent stores are not used in `v0.1.0`.

## Refresh model

Discovery runs only while the Avatar Doctor window is active:

- once when the window becomes usable after `OnEnable`/UI construction;
- immediately when the user invokes `Refresh`;
- after `EditorApplication.hierarchyChanged`;
- after a loaded scene is opened or closed; and
- when an observed invalid candidate requires the result to be rebuilt.

Hierarchy and scene events schedule one coalesced delayed refresh. Repeated events while a refresh is pending do not schedule additional scans. There is no `Update`, `OnInspectorUpdate`, polling loop, background thread, or per-frame scan.

`Selection.selectionChanged` re-evaluates automatic selection against the current candidates and does not scan merely because selection changed. It cannot override a valid manual selection.

Subscriptions are instance-owned and symmetric:

1. `OnEnable` defensively removes then adds each supported callback once and schedules the initial discovery after the UI is usable.
2. `OnDisable` removes every callback and any pending delayed callback.
3. Window close therefore leaves no active Avatar Doctor callbacks.
4. Domain reload reconstructs the window lifecycle and cannot accumulate duplicate subscriptions.

The explicit Refresh action cancels any redundant pending delayed refresh before publishing its new result.

## UI contract

The existing code-only UI Toolkit window becomes the discovery surface. The release does not introduce UXML, USS, presentation assets, a new design system, or a broad application redesign.

### Zero avatars

- Show a clear empty state: `No VRChat Avatar Descriptors found in the loaded scene(s).`
- Keep the Refresh action available.
- Show no stale selected avatar.

### One avatar

- State that one avatar was found and selected automatically.
- Show the GameObject name, hierarchy path, and scene identity.
- Keep the Refresh action available.

### Multiple avatars

- Show the candidate count.
- Provide one manual selection control containing every candidate in deterministic order.
- Identify entries with scene identity and indexed hierarchy path so duplicate names remain distinguishable.
- When multiple descriptors share one GameObject, append a one-based descriptor ordinal such as `Descriptor 1` and `Descriptor 2` only to the otherwise ambiguous entries.
- Never expose Unity InstanceID as candidate identity or UI text.
- Show the selected candidate and selection origin clearly.
- If no automatic choice is safe, instruct the user to choose an avatar.
- Keep the Refresh action available.

## Safety invariants

- `DISCOVERY-01` — Discovery never mutates scene, asset, or project state.
- `DISCOVERY-02` — Only descriptors belonging to regular valid loaded non-preview scenes are returned.
- `DISCOVERY-03` — Inactive avatar roots and descendants remain discoverable.
- `DISCOVERY-04` — Candidate ordering follows the defined deterministic key.
- `SELECTION-01` — Exactly one candidate is selected automatically.
- `SELECTION-02` — Multiple candidates are never resolved by arbitrary enumeration order.
- `SELECTION-03` — A valid manual selection is never silently overridden.
- `SELECTION-04` — An invalidated candidate cannot remain selected.
- `LIFECYCLE-01` — Editor event subscriptions cannot accumulate across window reopen or domain reload.
- `UI-01` — Zero, one, and multiple states and otherwise identical same-root descriptor entries are visibly distinguishable.
- `SDK-01` — VRChat integration uses the approved package and supported public SDK boundaries.
- `ERROR-01` — An unexpected discovery or selection failure preserves the last consistent state and never mutates project state as recovery.

## Failure behavior

| Condition | Required behavior |
| --- | --- |
| Descriptor destroyed during refresh | Exclude the destroyed reference, complete with the remaining live candidates, and apply selection invalidation. Do not publish a null candidate. |
| Scene unloaded | Remove every candidate from that scene on the coalesced refresh and rerun selection rules. |
| Preview scene or Prefab Stage present | Exclude every descriptor in that preview scene. A prefab asset opened in Prefab Mode never becomes a candidate; an instance in an eligible regular scene remains eligible. |
| Duplicate GameObject names | Distinguish entries with scene identity and indexed hierarchy path; names alone never establish identity. |
| Nested descriptors | Discover each descriptor; map Editor selection to the nearest unique descriptor ancestor. |
| Multiple descriptors on one root | Preserve each candidate's component ordinal and show a one-based ordinal only where the entries would otherwise be ambiguous. Treat automatic root mapping as ambiguous unless a valid selection already identifies one. |
| Active selection outside avatar roots | Make no new automatic choice; preserve a valid automatic choice or remain unresolved. |
| Selected candidate becomes invalid | Clear it before publishing state, clear stale manual origin, and rerun automatic rules. |
| Window closed and reopened | Remove old callbacks, construct a fresh instance state, subscribe once, and run initial discovery. |
| Domain reload | Reconstruct non-persistent state and subscriptions without duplicates, then run initial discovery. |
| Unexpected discovery or selection exception | Preserve the last internally consistent discovery and selection state, log the exception with clear Avatar Doctor context, show the transient operational error in the window, and keep Refresh available. |

### Unexpected operational errors

The window/controller boundary catches an unexpected exception escaping a discovery or selection operation. It must:

- leave the last internally consistent discovery result and selection unchanged;
- log the exception to the Unity Console with clear Avatar Doctor context and the failed operation;
- display a transient operational error message in the existing window without replacing the preserved candidate state;
- keep the explicit Refresh action available;
- clear the transient error only after a later Refresh completes successfully; and
- never mutate scenes, assets, objects, components, or project state as recovery.

This is a release-local operational failure surface, not a diagnostic finding system or general logging framework. Exceptions are not silently swallowed because the Unity Console retains the exception and its context.

## Testing strategy

Tests protect the contracts and invariants rather than a coverage target.

### Pure logic tests

Selection and state decisions must be separable from Editor UI rendering and cover:

- zero candidates;
- one candidate;
- multiple candidates with no safe automatic choice;
- deterministic ordering keys;
- manual selection preservation;
- manual selection invalidation followed by automatic resolution;
- automatic selection from an active nested object;
- active selection outside all avatar roots;
- nearest-ancestor resolution for nested descriptors; and
- ambiguous equal-depth descriptors;
- preservation of the last consistent state when an operation fails; and
- clearing a transient operational error after a successful Refresh.

### Unity Editor integration tests

Where practical, Editor tests use real scene GameObjects and official descriptor components to cover:

- no descriptors;
- one descriptor;
- multiple descriptors;
- an inactive descriptor root;
- multiple loaded scenes;
- duplicate names;
- multiple descriptors on the same GameObject with deterministic ordinals;
- deterministic ordering;
- loaded-scene filtering;
- preview-scene and Prefab Stage exclusion;
- refresh after hierarchy changes;
- destroyed descriptors and unloaded scenes;
- Avatar Doctor-context exception logging and preserved state on an injected operation failure; and
- lifecycle callback cleanup where observable.

Tests must confirm that discovery does not dirty scenes or mutate objects or assets.

### Manual Unity validation

The completed feature requires Unity `2022.3.22f1` validation of:

- package import and compilation;
- zero-, one-, and multiple-avatar states;
- manual and automatic selection;
- an inactive avatar;
- explicit Refresh;
- multiple loaded scenes;
- duplicate names;
- a prefab asset containing a descriptor opened in Prefab Mode remains excluded;
- an instance of that prefab in a regular eligible scene remains discoverable;
- same-root descriptor entries are distinguishable without displaying InstanceID;
- window close and reopen;
- domain reload behavior;
- no Avatar Doctor errors or warnings caused by the feature;
- no unintended scene dirtying; and
- no unexpected tracked or generated changes.

GitHub Unity-license CI is not introduced by this release without separate approval. `Repository Validation / validate` remains the required GitHub check.
